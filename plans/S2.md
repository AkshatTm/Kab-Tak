## Design calls this plan makes (SPEC/IMPLEMENTATION_PLAN are silent; recorded in T1)
1. **`POST /api/chat` returns cards that are already `POST /api/tasks` bodies.** The card carries `category_id` and `part_type_id` (names from the LLM are resolved against the DB; an unknown category becomes `null`, an unknown part type becomes `other`). Confirming a card is therefore exactly `POST /api/tasks` (S1), nothing new.
2. **Response shape:** `{intent, reply, cards: [Card], parsed: bool, parse_json}`. SPEC's single `card?` becomes `cards` (the first card plus `extra_tasks`, tentative ones flagged). `parse_json` is the raw validated LLM output, kept by the UI only to build a correction.
3. **Corrections:** a new `POST /api/corrections {raw_text, llm_output_json, corrected_json}` stores a `corrections` row. The UI calls it only when the user edited the card before confirming (compare against the original card). `task_id` is not in the chat response (nothing is persisted until confirm, D7/D8).
4. **ADR 0004 guard in code, not only in the prompt:** if the user text contains no digit and no number word (`one…twelve`, `half`, `quarter`, `ek`, `do`, `teen`… minimal list) and no time unit word, `estimate_min` is forced to `null` after parsing. `shortcut:` heuristic; upgrade if the eval shows false nulls.
5. **Intents handled in S2:** `create_task` (card), `question` / `unknown` (text reply, no card). Other intents (`update_task`, `stop_with_outcome`, `retro_log`, `plan_check`) are recognised by the schema but answered with "not available yet" until S3/S9/S10. The fast path (`start`, `break`, `done`…) is S3.
6. **All providers fail or no key configured:** HTTP 200 with `parsed=false`, one empty card whose `title` is the user's text, and the reply "Couldn't understand that — fill the card manually" (SPEC §2.3). A missing key skips that provider silently; if none is configured the reply says so.
7. **Keys:** a small `ProviderKeys` settings class reads `GROQ_API_KEY` etc. from the environment and the repo `.env` (no `KABTAK_` prefix). Keys never appear in responses, logs, or `llm_calls`.
8. **Sequential calls:** worst case is three providers each with a repair retry, one after another. `shortcut:` the sync route blocks a worker thread for that long; the UI shows a pending state. Upgrade if latency hurts.
9. **Prompt file is package data** (`app/chat/prompts/parse_task.md`, read with `importlib.resources`). S4 must add it to the PyInstaller bundle; noted in PROGRESS.

## Tasks (T2, T3, T4 are independent → parallel subagents; T1 first inline; T5 after T2+T3; UI after T5)

**T1 Provider verification + config + SPEC (inline)**
- Verify, in each provider's current docs (use the `web-fetch` agent), the OpenAI-compatible base URL and a current JSON-capable model id for Groq, Cerebras, Gemini (AI Studio). Check `response_format={"type":"json_object"}` support per provider; record any provider that needs a different knob.
- Write `config/llm.toml` with the verified ids, base URLs, `timeout_s = 8`, and a comment `# verified YYYY-MM-DD against <doc url>` per provider (today's date).
- `cd backend; uv add openai`.
- SPEC §3.3: `POST /chat` returns `{intent, reply, cards, parsed}`; add `POST /corrections`. SPEC §2.4: S2 handles `create_task`, `question`, `unknown`. §3.2: note the ADR 0004 guard. `CHANGES.md` entry.
- No tests (docs/config).

**T2 LLM chain** (`backend/app/llm/`) — independent
- `app/llm/config.py`: load `config/llm.toml` with `tomllib` into frozen dataclasses (`ProviderConfig(name, base_url, model, key_env)`, `LlmConfig(timeout_s, providers)`); `ProviderKeys(BaseSettings)` for the three keys (repo `.env`, no prefix). Path resolved relative to the repo root; overridable for tests.
- `app/llm/chain.py`: `class LlmChain(config, keys, engine, http_client_factory=None)` with `complete_json(messages, schema: type[T]) -> T | None`. Per provider in config order (D14, ADR 0002): skip when the key is empty; `openai.OpenAI(base_url, api_key, timeout=timeout_s, max_retries=0)`; `response_format={"type":"json_object"}`; validate with the Pydantic `schema`; on a validation failure one repair call that includes the validation error; then fall through. Fall through immediately on 429, 5xx, timeout, connection error, and on 401/403/400 (bad key or request). Returns `None` when every provider fails. Every API call (including the repair call) writes one `llm_calls` row (provider, model, latency_ms, ok, error text without any key, prompt/completion tokens when present).
- **Tests first** (`tests/test_llm_chain.py`, `httpx.MockTransport` injected through the SDK's `http_client`; DB = `migrated_url`): 429 → next provider succeeds; timeout → next; 500 → next; bad JSON → repair prompt contains the validation error → success on repair; bad JSON twice → next provider; 401 → next; no key for a provider → skipped with no call and no row; all fail → `None` with one `llm_calls` row per attempted call and `ok=False`; success → row `ok=True` with token counts; the api key string never appears in any stored `error`.

**T3 Chat parsing** (`backend/app/chat/`) — independent (uses a fake completer, not the real chain)
- `app/chat/schema.py`: Pydantic `ParseResult` exactly as SPEC §3.2 (`intent` enum with the seven values, `task`, `extra_tasks`, `confidence`, `clarifying_question`; `ParsedTask` with `category`, `estimate_min: int | None > 0`, `familiarity`, `tentative`, `parts[{type, quantity, unit}]`).
- `app/chat/prompts/parse_task.md`: the system prompt. It must state the intent list, the schema, the category and part-type lists (injected), that **durations are never invented or suggested** and `estimate_min` comes only from the user's words ("1.5 hours" → 90, "ek ghanta" → 60), Hinglish is allowed, tentative wording ("maybe", "if time", "shayad") sets `tentative`, and that multiple tasks go into `extra_tasks`.
- `app/chat/service.py`: `ChatService(engine, completer)` where `completer.complete_json(messages, ParseResult)` is the chain's method. `parse(text) -> ChatResponse`: builds messages (system prompt + categories + part types + the latest 10 `corrections` as few-shot pairs `raw_text → corrected_json`), calls the completer, applies the ADR 0004 guard (design call 4), resolves names to ids (design call 1), maps intents (design call 5), and returns the failure shape (design call 6) on `None`.
- **Tests first** (`tests/test_chat_service.py`, fake completer returning recorded `ParseResult`s): the "Video 2…" sentence → one card with 3 parts, correct ids, `estimate_min=90`; **no-estimate sentences (≥ 5, incl. Hinglish) → `estimate_min is None` even when the fake model returns a number** (ADR 0004 guard); sentence with a number keeps the estimate; unknown category → `category_id None`; unknown part type → `other`; `extra_tasks` → extra cards with `tentative` kept; intent `question`/`unknown` → reply, no card; unsupported intents → "not available yet"; completer returns `None` → `parsed=False` + one empty card with the user's text as title; few-shot block contains the latest 10 corrections newest first and none when the table is empty; the prompt text contains the "never invent durations" rule (guards against someone deleting it).

**T4 Eval set** (`backend/tests/fixtures/chat_eval.jsonl`, `backend/tests/test_chat_eval.py`) — independent
- ≥ 25 sentences with gold labels: `{text, intent, n_tasks, tasks:[{category, estimate_min, tentative, familiarity, parts:[{type, quantity}]}]}`. Cover: the "Video 2…" sentence, plain English, Hinglish, multi-task, tentative, no-estimate (≥ 6, gold `estimate_min: null`), hours vs minutes, assignment/project/admin, question and unknown intents.
- `test_chat_eval.py` is `@pytest.mark.live` (excluded by default): runs the real chain, scores **per field** (intent, n_tasks, category, estimate_min, tentative, familiarity, parts type+quantity), prints a per-field and overall accuracy table, and **fails below 90% overall**. A second, non-live test validates that every fixture line parses against the gold schema (so a bad fixture fails CI, not the live run).
- **Tests first:** the fixture-validity test (≥ 25 lines, every line valid, ≥ 6 no-estimate lines, ≥ 3 Hinglish).

**T5 API** (`backend/app/api/chat.py`, `backend/app/main.py`) — after T2 + T3
- `POST /api/chat {text}` → `ChatResponse`; `POST /api/corrections` → 201 with `{id}`; empty/whitespace `text` → 422. `Card` is a Pydantic model that is field-compatible with `TaskCreate` (`source` defaults to `chat`, `raw_text` set to the user's text).
- Wire `LlmChain` + `ChatService` lazily on `app.state` (like `get_service`); `create_app(settings, clock, completer=None)` lets tests inject a fake. No chain is built at import or at `python -m app.openapi`.
- **Tests first** (`tests/test_chat_api.py`, TestClient + fake completer): 401 without the token on both routes; chat happy path returns cards with ids that `POST /api/tasks` accepts unchanged (round trip: chat → confirm → `GET /api/tasks/{id}` is `ready` with the parts); all-fail returns 200 `parsed=false`; 422 on empty text; corrections stored and then appear in the next chat's few-shot (assert via the fake completer's captured messages); the response and the DB contain no key material (set a recognisable fake key in the env and grep the JSON).
- Regenerate `openapi.json` and `schema.ts` (D11).
